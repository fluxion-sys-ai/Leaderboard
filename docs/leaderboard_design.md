# Leaderboard HTML — Design Doc

Status: **spec / not yet implemented.** Target redesign for `leaderboard.html`
(generated by `src/report/build_leaderboard.py`). Captured 2026-08-04 from shujun.

## Goal

Restructure the leaderboard into **three clearly separated sections**, in this order:

1. **Raw benchmark scores** — every individual benchmark score per model.
2. **By-dimension view** — individual scores grouped by dimension + per-dimension average.
3. **Summary averages** — full flat average, then dimension-weighted average.

A guiding rule throughout: **always show all individual benchmark scores** — the
dimension/average sections *add* rollups, they never hide the underlying numbers.

Keep the existing hard constraint: **self-contained HTML** (no external JS/CSS/CDN;
all sort logic inline vanilla JS).

---

## Section 1 — Raw Benchmark Scores (per-model × per-benchmark)

- **One row per model.**
- **Default row order: by model size, DESCENDING (big → small).** MoE models sort by
  *total* params. Implemented in `build_leaderboard.py` (`model_size()` parses the name;
  `SIZE_OVERRIDE` handles odd ones like phi-4-mini). **Status: IMPLEMENTED 2026-08-04.**
- **Columns = every individual benchmark**, in dimension-grouped order:
  `ifeval, jsonschemabench, gsm8k, aime2026, mmlu_pro, zebralogic, gpqa_diamond,
  livecodebench, humaneval, cruxeval, babilong, ruler, writing, bfcl, pinchbench`.
- **Interaction — click-to-sort:** clicking a **benchmark column header** sorts the
  table by that benchmark's score (toggle desc/asc on repeat click). Clicking the
  **model / size header** returns to the default size ordering.
- Show `n` and scorer on hover/tooltip (as today).

## Section 2 — By-Dimension View

- Same models, but columns/blocks grouped by **dimension**. For each dimension, show:
  - **all the individual benchmark scores** that compose it, AND
  - the **dimension average** (mean of that dimension's benchmarks for the model).
- **Interaction — sort by dimension:** clicking a **dimension header** (e.g. "Agentic",
  "Reasoning") sorts the models by that **dimension average**.
- Never collapse to averages-only — the member benchmark scores stay visible next to
  each dimension average.

## Section 3 — Summary Averages (separate section)

- **Full average** — flat mean across all scored benchmarks per model.
- **Dimension-weighted average** — mean of the 7 dimension-averages (each dimension
  counts equally regardless of how many benchmarks it contains), per model.
- Present both, clearly labeled as distinct columns, in their **own section**.
- Sortable by either.

## Dimension mapping (current — source: `build_leaderboard.py`)

| Dimension | Benchmarks |
|---|---|
| Instruction | ifeval, jsonschemabench |
| Reasoning | gsm8k, aime2026, mmlu_pro, zebralogic, gpqa_diamond |
| Coding | livecodebench, humaneval, cruxeval |
| Long-context | babilong, ruler |
| Writing | writing |
| Agentic | bfcl, pinchbench |
| ~~Factuality~~ | ~~simpleqa~~ — **currently excluded from averages** (dropped from board) |

→ **7 active dimensions.** The dimension-weighted average = mean of these 7 dimension
averages. simpleqa is still *scored and displayed* in Section 1/2 but does **not**
enter either average unless Factuality is re-enabled.

## Why two different averages?

- **Full (flat) average** rewards models that are broadly strong across *many*
  benchmarks, but lets a benchmark-heavy dimension (e.g. Reasoning's 5 benchmarks)
  dominate.
- **Dimension-weighted average** gives each of the 7 dimensions equal say, so a model
  can't win on Reasoning volume alone — it must be balanced across capability areas.

## Implementation notes / open items

- Need a **param-count field per model** (total + active for MoE) to drive size
  ordering — add to `configs/models.yaml` or derive from the name (`24B`, `26B-A4B`,
  `35B-A3B`). Prefer an explicit field to avoid parse ambiguity.
- All three sections render from the same in-memory score matrix; only ordering /
  grouping differs. Sorting is client-side (inline JS) so a single generated file
  supports all interactions with no rebuild.
- Missing scores (e.g. a model that hasn't run a benchmark, or an un-judged writing)
  render as `—` and are excluded from that model's averages (don't count as 0).
